JOBHUNTER: PIPELINE ANALYSIS, WEAKNESSES, AND THE V2 REBUILD

I read all 7,217 lines of the original (server.py, app.js, index.html, styles.css, the git history and the seeded database). I also ran the backend on test inputs. Every number below comes from those runs, not from the README.

PART 1. HOW THE ORIGINAL WORKS, PATH BY PATH

The app is a Python standard-library HTTP server with one SQLite file and a browser front end. One user, one profile (row id 1). Nothing runs in the background.

Path A. Resume intake
  Browser file picker
    -> FileReader.readAsText (also used for PDF and DOCX)
    -> POST /api/parse-resume with the raw text
    -> server regex finds the email, the phone, and skill keywords
    -> everything else is a hardcoded placeholder
       (name = first line, years = 5, employer = "Recent Tech Employer",
        school = "University / College", title = "Software Engineer")
    -> profile form -> POST /api/profile -> SQLite

Path B. Search
  GET /api/search
    -> in-memory cache lookup (key = query + location, 15 minutes)
    -> 7 tasks in parallel: LinkedIn scraper, Remotive, Jobicy, Arbeitnow,
       RemoteOK, ONE Greenhouse board (gitlab, first 10 jobs), and a catalog
       of 8 invented sample jobs
    -> merge and deduplicate
    -> score every job against the profile
    -> filter by min score, work mode, location -> JSON

Path C. Match score (0 to 100)
  55 points skill coverage, up to 12 for sister skills, 20 title words,
  10 work mode, 5 seniority. The result is clamped between 28 and 99.

Path D. Resume refiner (side-by-side diff)
  String templates. No language model. Produces a summary, a skill order and
  bullet edits. The user accepts or rejects each diff in the browser.

Path E. 1-click auto-customize
  Same templates plus a hardcoded 95 to 99 ATS target. Reports "speed_ms: 32"
  as a constant.

Path F. 1-click auto-hunt
  Runs the resume rewrite, cover letter and interview prep, then inserts a row into the
  tracker with status "applied". Nothing was submitted anywhere.

Path G. Gap report, cover letter, interview prep
  Templates keyed on a fixed list of "common" and "deep" skills.

Path H. Tracker (kanban): five columns, one row per application, no history.
Path I. Watchlist: stores company, slug and board type.
Path J. Digest: one endpoint which re-runs a search and returns the top six.
Path K. Export: txt, an HTML file renamed .doc, and browser print for PDF.
Path L. Purge: deletes three tables.

PART 2. WEAKNESSES AND GAPS

I rank them by damage to the user. Items marked (verified) I reproduced by running the code.

CRITICAL: the product breaks its own promises

C1. Deduplication deletes real jobs (verified).
    The title tokens loop iterates over characters, so the key is only the
    company name. I fed it 3 different Stripe roles plus 1 true duplicate. It
    returned 1 job. Every search silently drops all but one role per company.

C2. The "never invents experience" guarantee is false (verified).
    For a candidate whose only skill is Excel, auto-customize returned the skills
    AWS, Docker, PostgreSQL, React, FastAPI and Python, and rewrote the summary
    to "Accomplished Software Engineer ... enterprise-grade systems". The
    refiner appends "99.9% service reliability" and "zero-downtime rollouts" to
    bullets whether or not they are true. The cover letter says "I led
    initiatives" and "followed the company's work" for every user. Submitting
    these documents is a risk to the candidate: false claims found in an
    interview or background check cost offers.

C3. The resume parser is mostly fake (verified).
    Only the email, phone and skills are read. Work history, education, years
    of experience and target title are invented. PDF and DOCX files are read
    as text, so they arrive as binary noise. The README says the parser
    "extracts years of experience, work history, and education".

C4. Fake jobs sit inside real results.
    Eight invented postings (Stripe, Datadog, Anthropic, Spotify and others)
    with made-up URLs and salaries are merged into every search. They carry
    labels like "Verified" and "Direct Company ATS". A user might apply to a
    page which does not exist.

C5. Auto-hunt records "applied" for jobs never applied to.
    The tracker then shows a false funnel and sets a follow-up date.

HIGH: wrong or misleading results

H1. Skill matching produces false positives (verified). In one sentence of
    ordinary prose ("go-to-market", "next quarter", "express lane", "AI",
    "shell", "spring") the matcher found 6 skills: Go, Next.js, Express,
    Spring Boot, Linux CLI, Artificial Intelligence. Aliases such as go, next,
    ai, shell, spring, ts, py and rs match everyday words.
H2. Scores are inflated and cannot go low (verified). An unrelated pastry chef
    posting scored 58 "Moderate Fit" for a software engineer, because of the
    28 point floor and free points for work mode and seniority. A 99 cap
    means nothing reaches 100.
H3. Most real postings carry no description. Greenhouse jobs get the text
    "Official public posting on ..." and LinkedIn jobs get a sentence built
    from the title. Description text is cut to 1,200 characters elsewhere. The
    scorer then has no requirements to read and falls back to a neutral score.
H4. Only 1 of the 5 advertised ATS families exists. Lever, Ashby,
    SmartRecruiters, Workable, Hacker News and Indeed appear in the README and
    UI but have no fetcher. Greenhouse is hardcoded to the gitlab board with 10
    jobs. The watchlist is never read by the search.
H5. The watchlist does nothing. It stores rows and writes "1 active match" and
    a fresh timestamp without calling any board.
H6. The digest is not a digest. It never sends, never schedules, and cannot
    tell new jobs from old ones.
H7. The ATS score is cosmetic. It has a floor of 35, a cap of 99, a layout
    check which always passes, and the auto-customize is tuned to raise it by
    inserting keywords.
H8. The location filter drops remote jobs. Searching "San Francisco" removes
    every role whose location text lacks the search string, including remote ones.

SECURITY AND PRIVACY

S1. Every API response sends Access-Control-Allow-Origin with a wildcard, and
    there is no token. Any web page the user opens gains read and write access
    to the resume, the records and the purge endpoint on 127.0.0.1:8080. DNS rebinding adds a second
    route.
S2. Exported HTML is built with f-strings and no escaping. Job titles and
    company names from public feeds flow into the customized summary and from
    there into the exported file (stored script injection).
S3. The purge does not remove the settings table, and the VACUUM step is
    missing, so deleted content stays in the file. A restart re-seeds the demo
    profile (Alex Rivera) so the app never reaches a truly empty state.
S4. The repository ships jobhunter.db, __pycache__ and a seeded fake identity.

RELIABILITY AND DATA

R1. One slow source blocks the whole search. The thread pool waits for every
    task, with timeouts of 3.5 to 5 seconds each and no overall deadline.
R2. Failures are print statements. The user sees an empty list with no hint
    about a source being down.
R3. The cache lives in memory only, never evicts, and one failed fetch
    caches an empty list for 15 minutes.
R4. No tests, no logging, no migrations, no pinned behavior. Any change risks
    silent breakage.
R5. Invalid JSON or a bad number in a query string crashes the handler with a
    stack trace.
R6. Salary text is invented ("Competitive", "Top-of-market") and never parsed,
    so salary cannot affect ranking.

PART 3. WHAT V2 CHANGES

Each row names the weakness it closes.

C1  dedup.py. Key = company plus normalized title tokens, with a fuzzy match
    inside one company and a location check. Test: 3 distinct roles stay 3.
    True duplicates merge, the ATS link wins, tracking parameters are removed.
C2  refit.py. A grounding check compares every number and skill in any output
    to the master resume. The deterministic engine only reorders and respells
    skills you already list (Postgres becomes PostgreSQL when the posting uses
    this form). The optional LLM engine (set ANTHROPIC_API_KEY) must pass the
    same check, and failing rewrites are dropped. Cover letters cite your real
    bullets and state real gaps ("I have not used Kubernetes professionally").
C3  resume_parser.py. Reads sections, dated jobs, schools, links, location.
    Computes years from merged date ranges. Reads DOCX and PDF on the server.
    Fields it cannot find stay blank and the response lists them.
C4  Sample jobs removed from live results. They exist only in demo mode
    (JH_DEMO=1) and carry the tier label "Sample (demo data)".
C5  Auto-hunt now saves a package with status "saved". You move the card to
    Applied. Every status change is stored with a time.
H1  skills.py. 121 skills in 13 categories (the original had 62, all
    technical). Ambiguous words match only in safe forms. Test: the prose
    sentence above returns zero skills.
H2  scoring.py. No floor and no cap. Weights: skills 50, title 20, seniority 10,
    work mode 10, freshness 5, salary 5. Required skills count more than
    "nice to have". A domain gate caps a job from another field at 32. Each
    result has a confidence level and a point breakdown. Pastry chef: 58 to 32.
H3  sources.py. Full descriptions up to 7,000 characters from every ATS, and a
    fetch-details step for SmartRecruiters and LinkedIn.
H4  Real clients for Greenhouse, Lever, Ashby, Workable, SmartRecruiters,
    Remotive, Jobicy, Arbeitnow, RemoteOK, We Work Remotely, Hacker News
    (Algolia), Adzuna (free key, covers local and non-tech jobs), plus always-attempted
    LinkedIn and Indeed (JobSpy or the built-in fallback). Search reads your watchlist, so any company
    on those boards is searchable.
H5  tracker.py. Adding a company auto-detects its board. "Check now" calls each
    board, counts matches for your target role and stores the result.
H6  digest.py. Returns roles first seen since the last digest above your
    threshold. Writes an HTML file and sends email through SMTP. A daily
    scheduler starts when JH_DIGEST_TIME is set.
H7  ats.py. Score = keywords 40, structure 16, contact 4, metrics 20, verbs 10,
    length 10. No floor, no cap, stuffing is penalized. Test: customizing does
    not raise the score by stuffing.
H8  pipeline.py. Location keeps remote roles. Work mode filters on a normalized
    value.
S1  httpd.py. Per-run session token on every API call, Host header allow-list,
    no CORS headers, 12 MB body limit, frame denial.
S2  exporters.py. All export formats escape their input.
S3  db.py. Purge clears every table and runs VACUUM. No fake identity: a new
    install starts empty. the database file is git-ignored.
R1  A 14 second overall deadline. Slow sources are named and skipped.
R2  Each source reports ok, cached, stale, failed, paused or timeout. The UI
    prints them under the search box.
R3  SQLite cache. A failed source serves its last good results (up to 24 hours)
    and says so. A circuit breaker pauses a source after 3 failures.
R4  28 unit tests, structured logging, schema versioning, a backfill step for
    old databases.
R5  Every endpoint returns JSON errors with a reference id.
R6  Salary is parsed to a number range and used in scoring. Placeholder words
    are dropped.

New capabilities:
  Real DOCX export and a text-based PDF export (extractable by ATS parsers).
  Funnel statistics: applied to interview rate, average days to interview,
  overdue follow-ups, status history per card.
  Excluded-keyword and minimum-salary preferences in the profile.
  New-job detection across searches (first_seen, is_new).
  Source health endpoint (/api/sources).

MEASURED RESULTS (same inputs, old versus new)

  Distinct roles kept from the dedup test        1 of 3     ->  3 of 3
  False skills found in the prose sentence       6          ->  0
  Pastry chef score for a software engineer      58         ->  32
  Skills added for an Excel-only candidate       6 invented ->  0 added
  Resume formats read correctly                  txt        ->  txt, md, docx, pdf
  Working job sources                            5 live + 8 fake -> 12 real (+2 always-attempted major boards)
  Company boards searchable                      1 (10 jobs) -> any on 5 ATS families
  Skills in the ontology                         62         ->  121
  Automated tests                                0          ->  28
  Search with every source down                  empty list, no explanation
                                                 -> returns in about 1 second and names each failure

I use "10X" for these measured gaps only. Where the old behavior was wrong, the
new behavior is correct, and no ratio captures it.

PART 4. WHAT V2 DOES NOT FIX

I want you to know these limits before you rely on it.

1. No test reached the live job sites from my build environment, so the
   network clients were tested against recorded response shapes, not live
   servers. APIs change. The circuit breaker and the source status line will
   show you quickly if one stops answering. Run the app once and check the
   status line.
2. The PDF reader handles ordinary text PDFs. Scanned PDFs need OCR. Install
   pypdf for a stronger reader, or paste the text.
3. LinkedIn and Indeed are attempted on every search as requested. LinkedIn's
   public endpoint and Indeed's page structure can still block or change; the
   source-health line, circuit breaker, and stale-cache fallback make that
   visible instead of silently disabling them. Indeed uses JobSpy when installed
   and a stdlib fallback parser otherwise.
4. Matching reads text, so it misses synonyms outside the 121-skill ontology.
   Extend the lists in jh/skills.py (one line per skill).
5. The LLM engine is optional and untested against the live API. The grounding
   check protects against invented claims, but you should still read every
   resume before you send it.
6. One user, one profile, local only. A multi-user version needs real
   authentication.
